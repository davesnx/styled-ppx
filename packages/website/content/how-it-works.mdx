# How it works

styled-ppx is a **compile-time** CSS system. This page explains what happens between writing `[%css "display: flex"]` and a browser painting your page.

## How the ppx fits in

Generally speaking, a ppx is OCaml's system for macros, similar to [babel plugins](https://babeljs.io/docs/en/plugins/): a small program that runs before compilation and transforms your source code.

styled-ppx expands four extensions:

| Extension | What you get |
| --- | --- |
| `[%css "..."]` | a [`CSS.styles`](/reference/runtime) value: class names plus (optionally) inline custom-property values |
| `[%styled.<tag> "..."]` | a React component for the given HTML tag |
| `[%styled.global "..."]` | global styles as a React component (`@font-face`, resets, `:root` variables) |
| `[%keyframe "..."]` | a typed `@keyframes` animation name |

If you are curious about the actual transformation, check the [snapshot tests](https://github.com/davesnx/styled-ppx/tree/main/packages/ppx/test/snapshot).

You can learn more about ppxes in [Tarides blog: Introduction to OCaml ppx ecosystem](https://tarides.com/blog/2019-05-09-an-introduction-to-ocaml-ppx-ecosystem).

## The pipeline at a glance

```
your .re / .ml source
  │
  ▼
① ppx expansion (while compiling each file)
   ─ parse & type-check the CSS
   ─ give each [%css] block one class
   ─ lower $(expr) interpolations to CSS custom properties
   ─ park the rendered CSS in [@@@css "..."] attributes
  │
  ▼
② dune builds your project normally
  │
  ▼
③ styled-ppx.generate (a dune rule you add once)
  │
  ▼
styles.css: a plain, static asset you link like any stylesheet
```

Your components carry the class names the ppx minted at step ①, plus, when you use interpolation, the values of a few CSS custom properties.

See [Setting up the dune rules](/getting-started/dune-setup) for the concrete build configuration.

## Blocks: one block, one class

Each `[%css]` or `[%styled.<tag>]` block becomes one class. Its declarations stay together in one rule, in source order:

```reason
/* card.re */
let layout = [%css {|
  display: flex;
  align-items: center;
|}];
```

extracts to:

```css
.css-1upa9t7{display:flex;align-items:center;}
```

and `layout`'s className is `"css-1upa9t7"`. A block with nested selectors or at-rules gives one rule for each of them, all on the same class.

Because a block is one rule, duplicate declarations of one property keep their order: in `display: -webkit-box; display: flex;` the later one wins, as in plain CSS.

### Class names

The format is `css-<hash>`. The hash covers the module name, the submodule path, the binding name, the block's rules after its selector references (`.$(x)`) are resolved, and its interpolated expressions. So:

- the same block compiled twice (for example a native and a Melange copy of one module) gets the same class, and `styled-ppx.generate` writes it once;
- two blocks with the same content in different modules or bindings get different classes;
- an empty block (`let marker = [%css {||}]`) writes no rule but still has a class, which selectors can reference.

The class has no label. Use the `--dev` flag (or `--env development`) to add a `cx-<binding>` marker class next to it, which you can search for in the DOM inspector.

If two different blocks get the same class, `styled-ppx.generate` fails and names both blocks.

### Cascade and ordering

Every block rule has the same specificity (one class), unless its selector adds more. The tiebreaker is stylesheet order: the later rule wins. `styled-ppx.generate` writes files in the order of its arguments, and the rules of a file in source order. When `CSS.merge` combines two blocks that set the same property, the block that comes later in the stylesheet wins; the argument order of `CSS.merge` has no effect. The full rules and the `:where()` pattern for defaults live in [Which declaration wins](/reference/runtime#which-declaration-wins).

## Dynamic values: CSS custom properties

Interpolating a value does **not** opt a block out of extraction. The ppx lowers `$(expr)` to a CSS custom property in the extracted rule:

```reason
let title = (~color) => [%css {|
  font-size: 2rem;
  color: $(color);
|}];
```

```css
.css-zvphd3{font-size:2rem;color:var(--zvphd3-0);}
```

The runtime side only supplies the property's *value*, through the element's inline `style` attribute (`style="--zvphd3-0:#667eea"`). That's why elements styled with interpolations carry a small `style` attribute: it holds variable definitions, never declarations.

A few details worth knowing:

- Variable names are `--<class hash>-<n>`, where `n` numbers the block's distinct interpolations in order (`--zvphd3-0` above), identical in dev and prod. Each block has its own variables: two blocks that interpolate the same expression use two different variables. The same expression read with the same type in several rules of one block (base, `&:hover`, `@media`) is one variable.
- The expression is wrapped in the typed `toString` for the property it's used in, so a `Color.t` where a length is expected is a compile error.
- Variables scoped to the element itself are registered with `@property { inherits: false }`, so updating one only recalculates that element's style, not its whole subtree.
- In `[%styled.global]`, interpolated values are supplied through a `:root { ... }` block rendered by the generated component instead of inline styles.

## Class references in selectors

Interpolating a *binding* in selector position (`&.$(active)`, `:has(.$(other))`) is resolved **statically**: the actual class names are substituted into the extracted CSS, with no `var()` indirection. Same-file references resolve during ppx expansion; references to bindings in *other modules* are resolved by the aggregator at stylesheet-generation time (one of the reasons the aggregator exists). Syntax, rules, and errors are documented in [Class references in selectors](/reference/selectors#class-references-in-selectors).

## The aggregator: `styled-ppx.generate`

The ppx runs one file at a time and cannot see the rest of your project, so each compiled file carries its extracted CSS in top-level attributes (`[@@@css "..."]`) that ride along in the build artifacts. `styled-ppx.generate` is a small CLI that:

1. walks the post-ppx `.ml`/`.pp.ml` files you point it at,
2. collects every extracted rule and binding export,
3. resolves cross-module selector references,
4. checks that no two different blocks have the same class,
5. deduplicates rules (order-preserving), and
6. writes the final stylesheet.

You wire it up once as a dune rule; the rule, CLI flags, and troubleshooting live in [Setting up the dune rules](/getting-started/dune-setup).

## What this buys you

- **Server rendering is just rendering.** Link `styles.css` in your `<head>` and render. No orchestration needed.
- **Cacheable CSS.** `styles.css` is a static asset with a stable content: it caches like any other file and can be served from a CDN.
- **Smaller JS.** Your bundle carries class-name strings, not a CSS engine.
